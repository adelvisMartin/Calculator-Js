# InSave Recovery Heavy — Engineering & Product Audit

Date: 2026-08-23  
Scope: Recovery v0.17.2 source reconstruction, Android packaging, extraction stack, status workflow, CI/QA and production-readiness.

## Executive assessment

InSave Recovery Heavy has a **strong functional recovery strategy but is not yet a production-grade codebase architecture**. Its greatest technical strength is extraction resilience: it preserves a local heavy runtime, isolates multiple provider paths and treats playlist entries as independent jobs. Its greatest weakness is structural: InSave is currently reconstructed by applying text/script patches over a pinned third-party Android engine. This is useful for recovery and reproducibility, but it is fragile for long-term ownership, large-team development and upstream upgrades.

## What is already professional

### Extraction resilience

The Provider A → B → optional C design is the correct direction for a downloader exposed to frequent upstream changes. Provider B remains local and packages Python/yt-dlp, QuickJS and FFmpeg rather than relying on a mandatory external API. Per-video token awareness is especially important because a playlist cannot safely be modeled as one global extraction transaction.

### Failure isolation

The batch policy treats each selected media entry as an independent immutable job. That avoids a single unavailable video cancelling an entire list and is a significantly more robust model than one monolithic playlist transaction.

### Local-first status discovery

The Recovery product contract intentionally restores automatic WhatsApp and WhatsApp Business discovery and keeps manual folder selection as fallback. The v0.17.2 work removes the previous visible-item truncation, adds search and makes the status grid scroll independently.

### Release philosophy

The project documentation correctly states that `ASSEMBLE PASS` is not a functional pass. Real Android conversion, multiple MP3 outputs and status discovery are required P0 behaviors. This is materially stronger than relying only on compilation or screenshots.

## Critical findings

### P0 — Dedicated release signing is missing

The pinned upstream Gradle configuration assigns the release build to a signing configuration named `debug`. That is acceptable for local recovery QA but is a **production blocker**. InSave needs a dedicated release/upload key, secrets outside source control, documented key rotation/recovery and—if Play is used—Play App Signing.

### P0 — Recovery source is patch-driven rather than owned source

The canonical Recovery build applies Python/string transformations to a pinned YTDLnis tree. A minor upstream refactor can invalidate anchors, silently skip a transformation or produce a semantically wrong patch even when source text still matches. The current approach should be frozen as the LKG recovery mechanism, not expanded indefinitely.

Target: create an owned InSave Android repository/fork where InSave code is normal Kotlin/Gradle source. Upstream changes should enter through reviewed merges/cherry-picks with contract tests.

### P0/P1 — Broad storage access is distribution-sensitive

Automatic direct `.Statuses` scanning currently depends on broad shared-storage access in the Recovery/sideload flow. This delivers the historical UX but creates a Google Play policy and privacy issue. A professional product should separate:

- `sideloadRecovery`: automatic direct-path access, clearly disclosed;
- `play`: SAF/MediaStore or another policy-compliant flow, with only the minimum required access.

Do not assume Play approval for `MANAGE_EXTERNAL_STORAGE` simply because the feature works technically.

### P1 — CI has false-negative risk

Previous v0.17.2 builds completed Gradle successfully, then failed the package job because a post-build grep/filename assertion was stale. CI should validate behavior and machine-readable artifacts instead of relying on fragile source-string checks. Build status files also modify the same recovery branch while other changes are being pushed, producing non-fast-forward/rebase noise.

Recommended: move status metadata to Actions artifacts/check summaries instead of committing run-state files into the source branch.

### P1 — Dependency/runtime alignment needs governance

The pinned engine uses youtubedl-android library/aria2c 0.18.1 while FFmpeg is 0.17.2. The build also contains older libraries and a deprecated Accompanist WebView implementation. This does not prove a vulnerability by itself, but it increases upgrade and compatibility risk.

Required controls:

- dependency catalog/BOM where practical;
- Dependabot or Renovate;
- OSV/Dependency-Check scanning;
- SBOM per release;
- license inventory/NOTICE;
- approved dependency update cadence;
- runtime checksum/signature verification.

### P1 — Gradle/Android deprecation debt

The build log reports deprecated Gradle property syntax, deprecated `archivesBaseName`/BasePluginConvention behavior and configured project directories that do not exist. Gradle warns that some of this behavior becomes an error in Gradle 9/10. The Android code also has widespread deprecated window/display/Parcelable APIs.

This debt should be treated as scheduled breakage, not cosmetic warnings.

### P1 — Exported component and intent input review

Recovery injection currently declares `InSaveHubActivity` exported. Any exported component increases the app’s externally reachable attack surface. If external launching is not a product requirement, make it non-exported. If it is required, explicitly validate action/data/extras, sanitize redirectable intents and protect privileged entry points.

### P1 — Native package size and binary surface

The Universal Heavy artifact intentionally packages Python, FFmpeg, FFprobe, aria2c and QuickJS for multiple ABIs. This is appropriate for Recovery QA but naturally creates a large APK and more native code to patch and audit. Build logs also show several native libraries that Gradle could not strip.

Maintain two distribution products:

- COMPLETE Universal QA/sideload artifact for device coverage and disaster recovery;
- ABI/AAB optimized production distribution, without removing required functionality.

## Code-quality findings

The prior Gradle compile reports several classes of warnings worth converting into tracked debt:

- Room query/model mismatch in `TerminalDao` (`TerminalItem.log` not returned by queries).
- nullable/safe-call concerns in `ZipUtils` and adapter code.
- repeated unnecessary `!!`, always-true/always-false conditions and unchecked casts.
- deprecated Display, system-UI, FragmentManager and Parcelable APIs across many UI classes.
- deprecated Accompanist WebView API in PO-token WebView flow.
- duplicate/deprecated Gradle declarations and missing module directories.

These warnings do not all represent current user-visible defects, but they are indicators of maintainability and future-compatibility cost. Establish a warning budget: new warnings fail CI; existing warnings are burned down by module.

## Scalability assessment

The current app is functionally extensible but structurally coupled. Adding another social provider or download feature today risks modifying shell code, provider routing, settings, database, workers and reconstruction patches together. A scalable design should make provider addition primarily an implementation of stable interfaces rather than a cross-repository patch exercise.

Recommended target modules:

- `:app` — composition root only.
- `:core:model`, `:core:ui`, `:core:network`, `:core:security`, `:core:storage`, `:core:testing`.
- `:domain` — use cases and provider-neutral contracts where reused logic justifies it.
- `:data:downloads`, `:data:library`, `:data:statuses`, `:data:settings`.
- `:provider:newpipe`, `:provider:ytdlp`, `:provider:cobalt`.
- `:runtime:ytdlp`, `:runtime:ffmpeg`.
- `:feature:home`, `:feature:statuses`, `:feature:downloads`, `:feature:followers`, `:feature:settings`, `:feature:player`.

Use interfaces at module boundaries and dependency injection at the app composition root. Each provider should return a shared typed result/error model.

## Recommended state and concurrency model

- UI state: ViewModel + `StateFlow`/UDF, one source of truth per screen.
- Persistent download state: Room as the source of truth.
- Long-running downloads: WorkManager with idempotent unique work and recoverable job IDs.
- Provider routing: deterministic policy object with bounded retry, timeout, health state and circuit-breaker behavior.
- Batch: immutable list of independent jobs, not shared mutable playlist state.
- Status gallery: repository emits immutable status lists; search/filter is a pure transformation over cached scan results instead of rescanning storage on every keypress.

## Security hardening priorities

1. Dedicated release signing and secret handling.
2. Separate sideload vs Play storage permission strategy.
3. Audit every exported activity/service/receiver/provider and every incoming intent.
4. Network allowlist/validation and TLS-only endpoints for configurable Provider C.
5. Never log cookies, tokens, signed stream URLs or full sensitive filesystem paths.
6. Verify downloaded runtime/update payloads before execution/replacement and retain rollback.
7. Add SBOM, dependency scanning and license notices.
8. Add malicious/invalid URL tests, oversized playlist/input limits and archive/path traversal tests around ZIP/runtime update code.

## Performance and UX hardening priorities

- Cache automatic status discovery results and debounce filtering without rescanning all directories.
- Thumbnail/image loading should be lifecycle-aware with bounded caches.
- Validate memory on galleries with hundreds/thousands of status items.
- Use baseline profiles/macrobenchmarks for startup and status-grid scrolling.
- Track download worker CPU/battery/network impact.
- Preserve a simple default UI; advanced yt-dlp/terminal settings stay behind diagnostics.
- Add accessibility labels, minimum touch targets, dynamic font tests and localization overflow tests.

## Release-readiness decision

**Current classification: Recovery QA candidate, not Production Stable.**

A Production label should require all of the following:

1. physical-device P0 pass on at least one representative Xiaomi/MIUI device plus stock Android;
2. dedicated release signing;
3. storage/distribution policy decision;
4. clean owned-source migration plan in progress or completed;
5. SBOM/dependency/license gate;
6. no open P0 security or data-loss issue;
7. reproducible release, checksums and rollback artifact;
8. documented support and update policy.
